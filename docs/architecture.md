# Архитектура

## Общая схема

```text
Telegram
   │ HTTPS Update
   ▼
Vercel handler ─┐
                ├─► PostgreSQL update queue ─► Queue Worker ─► Bot App ─► Telegram Bot API
Node HTTP server┘                                  │               │
                                                  │               ├─► Redis: кеш сообщений и `/percent`
                                                  │               ├─► Analytics/Birthday ─► PostgreSQL
                                                  │               ├─► Cinema Monitor ─► Ticketon + PostgreSQL
                                                  │               ├─► Media Service ─► yt-dlp + ffmpeg
                                                  │               └─► isolated `/q` child ─► Satori + Sharp
                                                  └─► retries, DLQ, per-chat leases
```

Обе входные точки создают только PostgreSQL queue и ingress. HTTP-запрос заканчивается после идемпотентного INSERT. Отдельный постоянный worker создаёт Bot App, Redis и тяжёлые зависимости, забирает задачи с ограниченной конкурентностью и сохраняет порядок по chat ID.

## Поток обработки Update

1. Входная точка проверяет webhook secret и валидирует `update_id`/chat ID.
2. Update классифицируется как `default` или `heavy` и вставляется в `telegram_update_jobs`; duplicate ID не создаёт вторую задачу.
3. Telegram получает HTTP 200 сразу после фиксации в PostgreSQL.
4. Worker арендует самый старый доступный update, одновременно захватывая lease чата.
5. `handleUpdate` проверяет allowlist, сохраняет Redis timeline одним pipeline и выполняет команду.
6. Успех переводит задачу в `completed`; ошибка получает retry с exponential backoff, а после лимита — `dead`.
7. Heartbeat продлевает lease. После падения worker просроченная задача автоматически возвращается в обработку.

Входные точки по проектному контракту отвечают 200 и при ошибке enqueue. Такая ошибка видна в логах/метриках, но update будет потерян; штатные ошибки уже зафиксированной задачи обрабатываются worker retries.

## Поток создания цитаты

Команда `/q N` должна быть ответом на первое сообщение. Ответное сообщение принудительно кешируется, затем из Redis выбираются сообщения с `message_id` от него включительно до сообщения-команды исключительно. Команды исключаются, ID сортируются по возрастанию, результат ограничивается `N` сообщениями.

Worker запускает для каждой цитаты отдельный дочерний Node.js-процесс. Он определяет фактического автора с учётом `forward_origin`, загружает аватар и медиа через Telegram API, строит дерево Satori, получает SVG и передаёт его Sharp. Итоговый WebP вписывается в область 512×430 без увеличения и получает прозрачный нижний отступ 82 px. Timeout или отмена завершают весь дочерний процесс через `SIGKILL`, поэтому зависший нативный render не остаётся внутри worker и не блокирует следующие задачи чата.

Если `/qs` отвечает непосредственно на Telegram-фото, Bot App выбирает его крупнейший вариант и передаёт отдельному renderer. Sharp применяет EXIF-ориентацию, пропорционально вписывает изображение в 512×512 без обрезки и без добавления фона, рамки, текста или полей, затем кодирует статический WebP размером не более 512 КБ. Одна из сторон результата всегда равна 512 px. Reply на созданный ботом стикер `/q` продолжает сохранять уже готовый файл без повторного рендера.

Фото-стикер сначала загружается в Telegram через `uploadStickerFile`; полученный `file_id` добавляется в набор отдельным JSON-вызовом `addStickerToSet`. Для reply на стикер `/q` используется его существующий `file_id`, поэтому скачивание и повторная загрузка не нужны.

## Поток создания демотиватора

`/demotivation <текст>` требует reply на фото, image-document, статический стикер или `video_note`. Bot App скачивает Telegram-файл; для видеокружка отдельный сервис через ffmpeg сохраняет первый кадр в JPEG и удаляет временные файлы. Renderer применяет EXIF-ориентацию и растягивает изображение до внутренней области 908×876 без обрезки. Satori строит чёрный шаблон 1084×1200 с белой рамкой и адаптивной Times New Roman-совместимой подписью, Sharp объединяет слои и возвращает JPEG для `sendPhoto`.

## Поток аналитики

Обычное сообщение сначала обновляет профиль пользователя в таблице `users`. Затем текст или caption очищается от URL, токенизируется и агрегируется в `word_counts` по чату, пользователю, слову и календарному дню.

Игры используют накопленные данные:

- кодовое слово случайно выбирается из топ-15 слов за 14 дней и действует три дня;
- подсказка использует лидера по выбранному слову за 14 дней;
- ежедневный выбор берёт случайного известного участника и сохраняет результат на текущую дату.

## Поток загрузки внешнего видео

Media Service извлекает из text/caption до трёх уникальных поддерживаемых URL. Для каждой ссылки Bot App показывает действие `upload_video`, а сервис запускает отдельный `yt-dlp` без shell. Видео скачивается во временную директорию, при необходимости объединяется или перекодируется ffmpeg в MP4, читается в память и отправляется методом Telegram `sendVideo` как reply. Временная директория удаляется в `finally` и при успехе, и при ошибке.

## Поток Percent Game

`/percent <параметр>` оценивает автора команды либо автора сообщения, на которое отвечает команда. Сервис нормализует параметр через aliases из JSON-конфига, затем читает Redis по Telegram user ID и каноническому параметру. Если результата нет, выбираются процент 0…100 и один шаблон ответа; пара сохраняется на 86 400 секунд. Chat ID не входит в ключ, поэтому результат пользователя одинаков во всех чатах до истечения TTL.

`/all` читает известные профили чата из PostgreSQL, добавляет администраторов и через Telegram проверяет, что каждый кандидат по-прежнему состоит в чате и не является ботом. Результат отправляется безопасными mention entities и при необходимости делится по лимиту длины сообщения. Полный список обычных участников Bot API не отдаёт, поэтому молчаливые пользователи, которых бот ещё не видел, могут отсутствовать.

## Поток дней рождения

Команда `/birthday` сохраняет дату и профиль автора в PostgreSQL для конкретного чата. Worker запускает interval-проверку календаря через PostgreSQL `scheduler_leases`: только одна replica выполняет tick. После заданного локального часа сервис поздравляет сегодняшних именинников и рассылает напоминания. Delivery markers остаются вторым уровнем идемпотентности.

## Поток мониторинга кино Ticketon

`/kino` отправляет inline-клавиатуру с фильмами и кинотеатрами Ticketon в Астане. Запрос каталога ограничен `category=cinema`, а главная категория ответа проверяется повторно, поэтому концерты и прочие мероприятия исключены. Callback query проходит через ту же durable queue и переключает PostgreSQL-подписку чата. Пустой список кинотеатров означает отсутствие фильтра.

Worker раз в час под lease `ticketon-cinema-seat-monitor` загружает будущие сеансы выбранных фильмов и публичные static/dynamic карты каждого подходящего зала. Сервис соединяет геометрию с наличием по ID и ищет последовательные свободные места в половине зала с более высокими номерами рядов. Перед Telegram API-вызовом `(chat_id, session_id)` атомарно фиксируется в `ticketon_notifications`. Текст оповещения передаётся общему механизму `/all`, поэтому к нему добавляются проверенные участники чата.

## Границы состояния

- Web-процесс хранит только метрики; worker также хранит кеш emoji, rate-limit buckets и созданные сервисы.
- PostgreSQL queue временно хранит полные pending/retry/dead updates. Payload completed-задачи очищается сразу.
- Redis хранит сокращённые Telegram-сообщения 90 дней, timeline максимум из 10 000 записей и результаты `/percent` с настраиваемым TTL (по умолчанию 24 часа).
- PostgreSQL хранит известные профили для `/all` и аналитики, агрегаты слов, игры, ежедневные выборы, дни рождения, Ticketon-подписки и markers отправленных уведомлений. Старые birthday markers очищаются через 400 дней, cinema markers — через 90 дней.
- Telegram хранит исходные файлы и стикерпаки.
- Временная директория ОС кратковременно хранит загружаемые видео; после каждого вызова она рекурсивно очищается.

Отсутствие Redis не мешает очереди и аналитике: circuit breaker быстро отключает кеш, `/q` не сможет получить timeline, а `/percent` вернёт сообщение о недоступном хранилище. PostgreSQL обязателен для webhook queue и worker.

## Внешние зависимости

- Telegram Bot API и Telegram File API;
- публичный JSON API Ticketon для киноафиши Астаны, сеансов и карт зала;
- Upstash Redis через REST;
- PostgreSQL через `pg`;
- jsDelivr для Apple emoji и резервного Twemoji;
- Satori для SVG-разметки;
- Sharp/libvips для обработки изображений.
- системные `yt-dlp` и `ffmpeg` для внешних видео; ffmpeg также извлекает первый кадр видеокружка.

## Существенные ограничения текущей реализации

- Автоматические тесты покрывают классификацию/enqueue, worker success/timeout/DLQ, rate limit, Redis circuit, Percent Game, media, дни рождения и отбор мест Ticketon. `npm run lint` выполняет только синтаксическую проверку файлов.
- Ticketon не требует авторизации для используемых read-only карт зала, но внутренние интерфейсы сайта могут измениться без обратной совместимости.
- Telegram API, Telegram File API, OpenAI, PostgreSQL, Redis, emoji CDN, yt-dlp и ffmpeg ограничены таймаутами; Apple emoji и Twemoji остаются независимыми fallback.
- Очередь даёт at-least-once: ошибка после частично успешного внешнего вызова может повторить этот побочный эффект.
- Одновременные вызовы ежедневного выбора могут вернуть разным запросам разных кандидатов: вставка защищена `ON CONFLICT`, но проигравший запрос не перечитывает сохранённую строку.
- Одновременные угадывания кодового слова могут сформировать несколько победных ответов, поскольку результат условного `UPDATE` не проверяется.
- Только ошибка `addStickerToSet`, похожая на отсутствие набора, запускает `createNewStickerSet`; остальные причины логируются и возвращаются пользователю как общий отказ.
- `/qd` передаёт Telegram любой `file_id` стикера без локальной проверки владельца набора; фактический контроль выполняет Telegram.
- Загрузка шрифтов зависит от `process.cwd()`, который должен указывать на корень проекта.
- Загрузка внешнего видео держит готовый файл в `Buffer` до окончания multipart-запроса, поэтому лимит файла должен учитывать доступную память процесса.
