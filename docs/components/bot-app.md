# Приложение Telegram-бота

Файл `src/bot/app.js` связывает Telegram Bot API, Redis, рендереры цитат, фото-стикеров и демотиваторов, извлечение кадра видеокружка, загрузчик внешних видео, сервис аналитики, Percent Game, дни рождения и монитор кино Ticketon. Чистая логика отбора и разметки упоминаний находится в `src/bot/mentions.js`, проверка входа `/demotivation` — в `src/demotivation/service.js`, а выбор reply-фото и сохранение в нумерованные наборы для `/qs` — в `src/sticker/service.js`.

## Публичный API

```js
createBotApp({
  env = process.env,
  redis,
  redisGateway,
  analytics,
  mediaDownloader,
  demotivationFrameExtractor,
  birthdays,
  kino,
  percentGame,
  dailySummary,
  rateLimiter,
  metrics
})
// → { api, chatAllowed, handleUpdate, notifyCinemaAvailability }
```

- `api(method, payload, options)` вызывает Telegram Bot API с таймаутом, метриками и ограниченными повторами для 429/5xx; при финальном `ok: false` бросает ошибку.
- `chatAllowed(chatId)` проверяет allowlist. Пустой список разрешает любой chat ID.
- `handleUpdate(update, { signal, lane })` — главный обработчик worker-задачи; abort signal проходит в сетевые и media-операции.
- `notifyCinemaAvailability(alert)` отправляет утренний дайджест обычным сообщением без упоминаний участников.

`BOT_TOKEN` читается из `env`. Отдельной ранней проверки токена нет: при отсутствии значения приложение создаст URL с `undefined`, а ошибка проявится на первом API-вызове. Числовой префикс токена используется как `botId`, чтобы исключить самого бота из ежедневного выбора и проверить автора стикера для `/qs`.

## Разбор команд

```js
parseCommand(message)
// → null | { name, count, args }
```

Парсер читает `text`, затем `caption`. Допускаются ASCII-команды из букв и `_`, необязательный `@botname` и произвольная строка аргументов. Поле `args` сохраняет строку без крайних пробелов, что позволяет передать дату в `/birthday`.

Числовой `count` ограничивается диапазоном 1…10. Словесные аргументы поддерживают совместимые формы:

- `/pidor list`, `/pidor reset`;
- `/codeword start`, `/codeword hint`, `/codeword stop`.

После нормализации они превращаются в команды с `_`. Для остальных словесных аргументов имя команды сохраняется, а count равен 1.

## Обработка обновления

`handleUpdate` поддерживает `message`, `edited_message`, кино-callback из `callback_query` и court vote из `poll_answer`. Если одновременно присутствуют `message` и `edited_message`, выбирается `message`.

Порядок действий:

1. проверить chat allowlist;
2. сохранить сообщение в Redis одним pipeline; ошибка открывает circuit breaker и не останавливает команду;
3. разобрать команду;
4. для обычного сообщения — записать аналитику, проверить кодовое слово и обработать media URL;
5. для команды — сохранить профиль автора без учёта слов;
6. для `q/qs/qd` — выполнить операцию с цитатой;
7. `/demotivation` передать в renderer, `/percent` — в Percent Game, `/all` — в обработчик упоминаний, `/kino` — в Kino Monitor;
8. команды дней рождения передать в Birthday Service;
9. для остальных команд — обратиться к Analytics Service.

Перед выполнением запроса применяется общий лимит пользователя в текущем чате: десятый запрос в скользящем окне 5 секунд включает паузу 60 секунд. В один счётчик входят обычные команды, `/q`, `/qs`, media URL, `#итогидня` и kino callbacks. Обычный разговор и poll answers не расходуют бюджет. Для сообщения с media URL аналитика сохраняется до проверки лимита, но загрузка может быть отклонена.

Для сообщений учитывается Telegram `date`, для редактирования — `edit_date`, поэтому задержка worker не растягивает окно отправки. Повтор обработки того же `update_id` не считается новым запросом. Десятый запрос и дальнейшие запросы во время паузы не выполняются; бот сообщает о паузе один раз, а новые запросы не продлевают её. После 60 секунд бюджет сбрасывается. Лимит хранится в памяти отдельного worker; при нескольких replicas счётчики не объединяются.

Неизвестные команды молча игнорируются, но профиль автора сохраняется в `users`. Текст любых команд не входит в статистику слов.

## Таймауты и деградация

- JSON Telegram API: `TELEGRAM_API_TIMEOUT_MS`, по умолчанию 15 секунд;
- multipart upload: `TELEGRAM_UPLOAD_TIMEOUT_MS`, по умолчанию 120 секунд;
- Telegram File API: `TELEGRAM_FILE_TIMEOUT_MS`, по умолчанию 30 секунд;
- Redis REST: `REDIS_TIMEOUT_MS`, по умолчанию 1 секунда;
- после ошибки Redis circuit открывается на `REDIS_CIRCUIT_OPEN_MS`, по умолчанию 30 секунд;
- `cacheMessage` объединяет SET/LPUSH/LTRIM/EXPIRE в один Upstash pipeline, а чтение цитаты использует MGET.

Ошибки Redis дают функциональную деградацию `/q` и `/percent`, но не заставляют worker повторять весь Telegram update.

## Демотиватор: `/demotivation <текст>`

Команда должна отвечать на Telegram-фото, document с MIME `image/*`, статический стикер или видеокружок (`video_note`). Из массива `photo` выбирается вариант с наибольшей площадью. Animated и video stickers не поддерживаются. Подпись нормализуется в одну строку и ограничена 100 Unicode-символами; пустая или слишком длинная подпись получает подсказку без загрузки файла.

После проверки Bot App показывает `upload_photo` и загружает исходник через общий `downloadTelegramFile`. Из `video_note` зависимость `demotivationFrameExtractor` сначала извлекает первый кадр; остальные изображения передаются без промежуточного преобразования. `createDemotivationRenderer().renderJpeg()` собирает итог, который отправляется как `demotivation.jpg` методом `sendPhoto` в reply на команду. Ошибка загрузки, ffmpeg или рендера логируется и превращается в пользовательский ответ, не прерывая webhook. Геометрия и pipeline описаны в [документации renderer](demotivation-renderer.md).

## Массовое упоминание: `/all`

Команда работает только в `group` и `supergroup` и требует PostgreSQL. Bot App получает сохранённые профили через `analytics.knownUsers`, добавляет текущих администраторов через `getChatAdministrators` и проверяет остальных сохранённых пользователей методом `getChatMember`. Проверка выполняется пачками по 10 параллельных запросов. В результат входят статусы `creator`, `administrator`, `member`, а также `restricted` с `is_member=true`; пользователи со статусом `left`/`kicked` и все `user.is_bot=true` исключаются.

Упоминания отправляются через entities типа `text_link` с URL `tg://user?id=<id>`, поэтому имена не интерпретируются как HTML или Markdown. Ответ привязан к сообщению-команде. Если список превышает лимит Telegram в 4096 символов, он делится на несколько сообщений; reply содержит первая часть.

Telegram Bot API не предоставляет метод полного перечисления обычных участников. Поэтому источником кандидатов служат авторы сообщений и команд, человеческие пользователи из `new_chat_members` и администраторы. Участник, которого бот ни разу не видел, может отсутствовать до первого сообщения, команды или события вступления. `getChatMember` гарантирован для других пользователей только когда бот является администратором; ошибки отдельных проверок логируются, а такой кандидат не упоминается.

Кино-монитор не использует этот helper: утренний дайджест Ticketon отправляется отдельно, без mention entities.

## Монитор кино: `/kino`

Команда работает в группах и отправляет корневое меню с общими подписками чата. Кнопки `Фильмы`, `Кинотеатры`, `Время` и `Мест рядом` открывают списки общих настроек; callback редактирует то же сообщение. Время задаёт самую раннюю допустимую сессию, а размер блока — от 1 до 6 соседних кресел. Кнопка `Проверить сейчас` сразу подтверждает callback, запускает проверку текущего чата в heavy-очереди и отправляет все найденные варианты одним reply. Автоматический монитор также объединяет варианты в одно утреннее сообщение на чат. Ошибка каталога показывается через `answerCallbackQuery`, а детали пишутся в log. Полный контракт scheduler и карты зала описан в [отдельном разделе](kino-monitor.md).

## Процентная игра: `/percent <параметр>`

Bot App передаёт исходное сообщение и полную строку аргументов методу `percentGame.playText`, затем отправляет полученный текст как reply на команду. Выбор цели, проверка параметра, случайный результат и Redis TTL остаются внутри Percent Game. Подробный контракт и формат `config/percent-game.json` описаны в [отдельном разделе](percent-game.md).

## Instagram Reels и TikTok

Для обычного сообщения Bot App вызывает `mediaDownloader.urlsFromMessage`. Каждая найденная ссылка обрабатывается последовательно:

1. Telegram получает `sendChatAction` со значением `upload_video`;
2. `mediaDownloader.downloadVideo(url)` возвращает MP4 в Buffer;
3. `sendVideo` отправляет multipart-файл с `supports_streaming=true` как reply на сообщение со ссылкой.

Ошибка одной ссылки сопровождается пользовательским сообщением и не мешает обработать следующие ссылки. Детальная ошибка, код media-сервиса и URL записываются в server log. Ссылки в распознанных командах не обрабатываются, поскольку синтаксис команды не допускает дополнительный URL.

## Redis timeline

Для каждого разрешённого сообщения сохраняется сокращённый payload:

```text
message_id, date, from, forward_origin,
text, caption, entities, caption_entities,
photo, sticker, video_note, video
```

Ключ сообщения: `chat:<chatId>:message:<messageId>`. Он живёт 90 дней.

Timeline: list `chat:<chatId>:timeline`. Новый ID добавляется слева, list обрезается до 10 000 элементов и также живёт 90 дней. Edited message может добавить повтор ID; при чтении повторы удаляются через `Set`.

`collectMessages(chatId, startId, count, beforeId)` читает до 10 000 ID, выбирает диапазон `startId <= id < beforeId`, сортирует по возрастанию, по одному загружает сообщения и исключает распознанные команды. Возвращается не более `count` элементов.

## Создание цитаты: `/q [N]`

Команда должна отвечать на первое цитируемое сообщение. Reply принудительно записывается в Redis, что полезно, если его не было в timeline ранее. Затем сообщения собираются до ID команды и передаются изолированному `renderStickerWebp` в отдельном дочернем процессе.

Готовый buffer отправляется через `sendSticker` как multipart поле `sticker`, имя файла `quote.webp`, с ответом на сообщение-команду.

Если дочерний renderer не завершился за `QUOTE_RENDER_TIMEOUT_MS`, Bot App принудительно завершает его, логирует и измеряет `quote_renders_total`/`quote_render_duration_seconds`, сообщает пользователю об ошибке и завершает queue job без повторного зависания. Сигнал отмены всей job также немедленно завершает дочерний процесс.

Без Redis `collectMessages` всегда пуст, поэтому даже `/q` для одного reply завершится подсказкой о кеше.

## Стикерпак: `/qs` и `/qd`

`/qs` поддерживает два вида reply:

- Telegram-фото: выбирается вариант с наибольшей площадью, исходник скачивается и напрямую преобразуется в WebP через `src/render/sticker.js`; пропорции сохраняются, обрезка, фон, рамка, текст и дополнительные поля не добавляются;
- статический, не video и не animated стикер, отправленный текущим ботом через `/q`: существующий Telegram `file_id` используется без скачивания и повторной загрузки.

Фото пропорционально вписывается в 512×512 так, чтобы одна сторона была ровно 512 px, и при необходимости повторно кодируется с меньшим quality до лимита 512 КБ. Image-document и обычный чужой стикер для `/qs` не принимаются.

Готовый WebP-файл фотографии сначала отправляется отдельным multipart-запросом `uploadStickerFile` с MIME `image/webp`. Полученный Telegram `file_id` передаётся JSON-объектом `InputSticker`; вложенный multipart attachment для `addStickerToSet` не используется. Владельцем служит `STICKER_SET_OWNER_ID`, а без него — автор команды. Для общего набора рекомендуется явно задать одного владельца.

Sticker Service проверяет содержимое через `getStickerSet`. Уже сохранённый стикер определяется по `file_unique_id` или `file_id` и возвращает существующую ссылку. Если набор отсутствует, он создаётся с этим стикером. При достижении 120 стикеров либо ответе `STICKERS_TOO_MUCH` сохранение продолжается в следующем наборе: `quotes_by_Bot` → `quotes_2_by_Bot` → `quotes_3_by_Bot`. Суффикс бота и лимит имени 64 символа сохраняются, заголовок получает номер. Старые стикеры не удаляются.

После перезапуска сервис начинает поиск с базового имени и находит следующий свободный набор через Telegram. Сохранения внутри процесса последовательны; конфликт `STICKERSET_NAME_OCCUPIED` при создании другой репликой повторно проверяет тот же набор. Поиск ограничен 100 проверками за запрос. После успеха ответ содержит ссылку на фактический набор. Ошибки прав и формата сообщаются пользователю; сетевые ошибки, 429 и 5xx передаются worker для повтора. Ошибки создания набора обрабатываются так же, как ошибки добавления.

Успех записывается в лог `sticker saved` с фактическим именем набора и признаком повторного сохранения. Метрика `sticker_saves_total` различает `saved`, `already_saved` и `error`.

`/qd` требует reply на любой стикер и вызывает `deleteStickerFromSet` с его `file_id`. Приложение не проверяет имя набора или автора; Telegram отклонит запрещённую операцию.

## Telegram API и файлы

JSON-вызовы получают `content-type: application/json`. Файловые вызовы используют `FormData` и не задают заголовок вручную, чтобы runtime добавил boundary.

`downloadTelegramFile(fileId)` выполняет два запроса: `getFile`, затем GET к `https://api.telegram.org/file/bot<TOKEN>/<file_path>`. Результат полностью загружается в `Buffer`.

## Ошибки и производительность

Необработанные ошибки Bot App доходят до queue worker. Отдельно перехватываются постоянные ошибки сохранения стикеров, ошибки получения участников для `/all` и ошибки `/demotivation`. Отправка серий сообщений и загрузка сообщений из Redis выполняются последовательно; проверки участников `/all` параллельны внутри пачки из 10 запросов.
