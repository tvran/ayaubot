# План доработки сохранения стикеров

Основание: доступные Railway-логи за 29 сентября — 6 октября 2026. 4–5 октября три запроса `/qs` завершились `STICKERS_TOO_MUCH`. Текущий лимит разрешал только два heavy-запроса за минуту. 6 октября год `0000` прошёл проверку даты, вызвал пять ошибок PostgreSQL и перевёл задачу в `dead`.

## Реализованные изменения

1. Вынести сохранение наборов в `src/sticker/service.js`. Проверять набор через `getStickerSet`, возвращать ссылку для уже сохранённого файла, создавать отсутствующий набор. При заполнении продолжать в нумерованном наборе с тем же Telegram bot suffix и ссылкой на фактический результат. Старые стикеры сохраняются.
2. Обработать заполнение между проверкой и добавлением, одновременное создание набора другой репликой и повтор queue job после успешного Telegram-вызова. Сохранять последовательно внутри процесса. Постоянные ошибки создания/добавления объяснять пользователю, временные передавать queue worker для повтора.
3. Заменить лимиты 10/2 за минуту единым счётчиком запросов человека в чате: первые девять запросов в скользящем окне 5 секунд проходят, десятый включает паузу ровно 60 секунд. Учитывать время отправки сообщения и уникальный `update_id`. Отклонённые запросы не продлевают паузу; сообщение о ней отправляется один раз. Обычный разговор не учитывается.
4. Отклонять `0000` в команде дня рождения до записи в PostgreSQL.

Telegram допускает до 120 стикеров в обычном наборе; имя должно сохранять `_by_<bot_username>` и длину до 64 символов. Источник: [Telegram Bot API](https://core.telegram.org/bots/api#addstickertoset).

## Проверка и выпуск

- Детерминированные тесты с подменой Telegram API: заполненный набор, повторное сохранение, перезапуск, одновременные запросы, конфликт имени и ошибки прав/создания.
- Тесты лимитера: девятый/десятый запрос, граница 5 секунд, запросы вне окна, минутная пауза без продления, независимость пользователей/чатов, задержка queue worker и повторы задачи. Проверка через Bot App охватывает `/qs`, обычные команды и ранние обработчики `#итогидня` и `/anecdote`.
- Обязательные проверки проекта: `npm run lint` и `npm test`.
- Выпустить новую версию worker из подготовленного кода. Миграции БД не нужны. Старые `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_COMMANDS`, `RATE_LIMIT_HEAVY` игнорируются; новые defaults — 5000 ms / 10 запросов / 60000 ms. Для группы рекомендуется явно настроить `STICKER_SET_OWNER_ID`.
- После выпуска проверить `/qs` на заполненном наборе, ссылку на продолжение и серию запросов. По Railway-логам проверить отсутствие повторяющегося `STICKERS_TOO_MUCH` и запись новой версии worker.

## Ограничения

Лимитер хранится в памяти worker: текущая Railway-конфигурация содержит одну worker replica. При увеличении числа replicas общий счётчик следует перенести в PostgreSQL или Redis. Пауза сбрасывается при перезапуске процесса. Проверка дубля выполняется в просматриваемых наборах, а не по общему каталогу всех исторических паков. Поиск ограничен 100 проверками за одно сохранение.

Instagram rate limit требует действующих cookies для нужных роликов; это отдельная настройка media-сервиса. Ответ HTTP 200 при внутренних ошибках webhook остаётся требованием проекта.
